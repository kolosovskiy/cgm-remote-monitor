# Архитектура

## Принцип

Любое обращение клиента из любого канала проходит один и тот же путь:

```
вебхук / IMAP  →  адаптер канала  →  ingestInbound()  →  контакт → диалог → сообщение → лид
                                                                 ↓
                                                      событие message.in → автоматизации
```

Адаптеры каналов (`server/src/channels/*`) не знают про лиды и воронки: они только превращают
формат внешней системы в `InboundMessage` и умеют отправить текст обратно. Вся бизнес-логика живёт
в сервисах (`server/src/services/*`) и реагирует на доменные события (`server/src/events.ts`).
Это позволяет добавлять каналы, не трогая ядро.

## Модель данных

| Сущность | Назначение |
|---|---|
| `Contact` + `ContactIdentity` | Клиент и его идентификаторы: телефон, email, Telegram id, Viber id, PSID Messenger, Instagram id, WhatsApp. Пара (тип, значение) уникальна, по ней входящее событие находит контакт. Телефоны нормализуются к `380XXXXXXXXX`. |
| `Pipeline` + `Stage` | Воронки и этапы. Этап может быть помечен как «успех» или «отказ», тогда лид закрывается при переносе. |
| `Lead` | Сделка/заявка. Привязан к контакту, воронке, этапу, менеджеру. `source` фиксирует канал, `customFields` хранит значения настраиваемых полей. История этапов в `StageHistory`. |
| `Conversation` + `Message` | Диалог в одном канале с одним контактом. Внешний id чата — ключ. Сообщения с `externalId` идемпотентны: повторный вебхук не создаёт дубль. |
| `Call` | Звонок из Binotel: направление, статус, длительность, ссылка на запись, менеджер (по внутреннему номеру). |
| `Task`, `Note` | Задачи с дедлайном и заметки в карточке. |
| `FieldDefinition` | Описание настраиваемых полей для лида и контакта. |
| `Automation` | Правило: событие, условия (JSON), действия (JSON). |
| `WebhookLog` | Сырые входящие вебхуки с результатом обработки. Для отладки интеграций и повторной обработки. |

## Как лид «склеивается» с обращениями

1. Заявка с сайта с телефоном создаёт контакт с идентификатором `PHONE` и лид.
2. Клиент звонит: Binotel присылает номер, `resolveContact` находит тот же контакт, звонок
   привязывается к открытому лиду. Если открытого лида нет, входящий звонок создаёт новый.
3. Клиент пишет в Telegram: у бота есть только Telegram id, контакт создаётся новый. Если клиент
   нажимает «поделиться номером», телефон добавляется к Telegram-контакту и история не теряется.
   Дубли можно объединить вручную (`POST /api/contacts/:id/merge`).
4. Пока у контакта есть открытый лид, новые сообщения из любого канала попадают в него, а не плодят новые.

## Автоматизации

Правило срабатывает на событие (`lead.created`, `lead.stage_changed`, `lead.assigned`, `message.in`,
`call.finished`, `call.missed`, `task.overdue`). Контекст собирается из события: `lead`, `contact`,
`message`, `call`, `toStage`, `leadCreated`. Условия сравнивают поля контекста (`lead.source`,
`contact.customFields.city`, `message.text`), все условия должны выполниться. Действия выполняются по
порядку; тексты поддерживают подстановки `{{contact.name}}`, `{{lead.title}}`.

Действия: `assign_round_robin`, `assign_user`, `move_stage`, `reply_same_channel`, `send_message`,
`create_task`, `add_note`, `webhook`. Новое действие добавляется одной веткой в `runAction()`.

## Безопасность

- JWT на 30 дней, пароли bcrypt. Роли `ADMIN` и `MANAGER`; настройки, пользователи, удаление
  доступны только администратору.
- Вебхуки защищены: общий секрет (сайт, Binotel, Telegram secret token), HMAC-подпись
  (Meta, WhatsApp, Viber). Сырое тело запроса сохраняется для проверки подписей.
- Все токены интеграций в переменных окружения, не в базе.

## Что сознательно отложено

- Очередь задач (BullMQ/Redis). Сейчас вебхуки обрабатываются синхронно в запросе. Для текущих
  объёмов это нормально, при росте нагрузки обработка переносится в очередь без изменения адаптеров.
- Вложения из email и мессенджеров хранятся ссылками, не скачиваются в своё хранилище (S3).
- Уведомления менеджерам в реальном времени (WebSocket). Интерфейс обновляется опросом каждые 8–20 секунд.
